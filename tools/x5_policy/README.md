累计超过 500 毫秒或原始帧无效时隐藏。这个显示窗口不授权动作，启动仍要求 100 毫秒内的
新鲜姿态和小于 15° 的总倾角，原生控制持续复查反馈与 40° 保护。

页面提供四个模型的独立入口。选择预览模型并点击「真实反馈推理 · 不动作」可检查对应模型输出，
不发送 ARM 或 TARGET。「俯身 · 单次」从已到位站姿开始，运行 4 秒；
「翻滚 · 单次」从已到位站姿开始，运行 1.9 秒；「起身 · 单次」先保持默认姿态 1 秒，
再运行起身模型，实际默认姿态且倾角小于 15° 连续保持 1 秒后停止，总时长最多 8 秒。
起身和翻滚需要额外确认软垫、空间与防跌保护，并允许机身翻转。
每轮结束都发送 STOP 并回读全部扭矩关闭，不自动切入行走、不自动重试或重新使能。
这是分别验证模型的手动入口；四个模型加载完成不能替代各模型的实机动作验证。
普通站姿与行走保留 40° 倾角停机，俯身保留 55°；起身与翻滚仅在明确启动的一轮内允许翻转。
所有模型仍要求新鲜反馈、15 个舵机在线且无故障、实际位置和目标均在已保存范围内。

若提示某个关节实际位置超出记录范围，页面表格会显示该关节的实际读数、范围和默认站姿。
确认全部扭矩关闭后，轻轻摆回安全范围，再启动站姿；遇到机械阻挡应停止，不修改校准来掩盖阻挡。
校准采集、舵机维护和运控严格切换串口所有权，运控连接时不会另开采集串口。

模型、依赖和本次运控配置仅写入 X5 的 `/dev/shm`，不改写系统盘。X5 重启会清除这次部署，
重新连接会复查板卡身份和日志；不匹配时保留停止状态并显示原因。校准原件和备份保存在笔记本。
部署证据保存在本地运行目录 `motion-*/ready.json`，持续反馈摘要在 `motion-*/live-state.json`；
失败、关闭证明也单独保存。现有 CONFIG 系统挂载固定核对，模型进程禁止系统盘和块设备写入。

当前使用上面的统一工作台，不同时运行两个串口服务。

## 接通实机接口

运动固件源代码位于 `tools/esp32_motion`，构建镜像与 SHA-256 清单位于
`output/esp32_motion/firmware-ram-gains`。安装前保留现有诊断固件备份，并确认鸭子被可靠支撑。
详细的引脚、协议和验证范围见 `tools/esp32_motion/README.md`。

安装后，停止占用 ESP32 COM 串口的诊断/舵机工作台及终端。一个串口只由一个控制器使用。
运动固件 UART0 COM 使用 921600 baud，ESP32 经 URT-2 接 1 Mbps 舵机总线；
LSM6DSR 接 SDA GPIO8 / SCL GPIO9。15 个舵机 ID 及反馈顺序为：
`10–14, 20–24, 30–34`。

在 X5 上由服务管理流程启动带真实串口的网页进程，等价命令为：

```sh
cd /root/xgoduck-policy
.venv/bin/python web_app.py --motion-port /dev/ttyUSB0 --port 8767
```

先关闭原来的 8767 网页进程，避免端口冲突。依赖包含 `pyserial==3.5`。
启动只连接、发送停止和读取状态，不会自动启用舵机；串口断线重连也不会自动恢复动作。
先确认页面显示实际舵机读数、15 个在线 ID、无故障和新鲜 IMU 数据。

## 手动完成本机校准

当前 X5 原生工作台因实物后脑与板卡／线束发生干涉，要求先记录本次连接的头颈避让位置。
在扭矩全部关闭、机身有支撑时，手动将头颈摆到有明确活动间隙的位置，勾选头颈间隙确认，
点击「记录当前头颈位置 · 不动作」。后台从 100 毫秒内的实际反馈记录 ID 30–33，
不发送 ARM/TARGET，不修改机械零点、方向、范围、IMU 或模型元数据。
固定站姿采用上述固定腿部参照，四个头颈关节保持记录角度；启动前任一头颈关节相对记录移位达到
2° 会拒绝启动，需重新摆稳、确认间隙并记录。记录仅在本次运控连接有效，重连或服务重启后
需重新记录；普通网页刷新不会丢失后台记录。动态模型的头颈运动尚未完成间隙验证，
平衡、行走、起身、俯身、翻滚由后端拒绝启动，不动作预览仍可使用。
此设置只解决已确认的固定站姿头颈避让，不代表双脚接地、机械零位或独立平衡已验证。

先支撑机身、双脚悬空，点击 **停止并释放**。每次“记录”只采集编码器，不转动关节。
全部零点、方向与范围保存在 X5 的 `calibration.json`，重启后保留；
这些校准设置不会写舵机 EEPROM、ID、零偏或永久 PID 参数。
运动固件在启用时设置本次运行所需的临时 RAM 增益；断电后不会保留这些增益写入。

1. **核对机械零姿态**：查看网页中的训练模型 `q = 0` 参考图与各关节正方向图，
   结合实际装配辨认关节，然后确认已核对参考。默认站姿包含弯曲角度，不能用作零姿态；
   出厂编码器 2047 和其他鸭子的零点也不能直接套用。
2. **记零点**：逐个用手缓慢摆到对应关节的模型零姿态，点击该行“记零点”。
   嘴部 ID 34 使用闭合位置作零点。遇到阻力不要强推；机械零姿态需要人依据参考确认。
3. **记录安全范围**：手动摆到保留机械余量的两个端点，编码器较小的一端记为下限，
   较大的一端记为上限。下限必须小于上限，零点可以位于端点；嘴部闭合零位常在端点。
   本接口不支持跨越 `4095 → 0` 的角度范围，需要先调整装配。
4. **核对转向**：手动朝模型的正角度方向小幅摆动，编码器增加时选 `+1`，减少时选 `−1`，
   并勾选“方向已核实”。嘴部 ID 34 以张开方向为正；15 个关节都需完成。
5. **核对 IMU 轴向**：机身坐标为 `+X` 朝前、`+Y` 朝左、`+Z` 朝上。
   根据真实安装、前后俯仰与左右侧倾，选择传感器原始轴到机身轴的映射并明确确认。
   三个轴必须不同且组成右手坐标系；水平静止时机身加速度应约为 `[0,0,+9.8] m/s²`。
6. **静止校准 IMU**：全部舵机释放后，保持机身水平静止，点击采样校准。
   后台采集约 2 秒、100 个独立样本，记录陀螺仪偏置。
   静止采样不能判断安装轴向；运动、倾斜或反馈中断会导致校准失败。

页面需要显示 15 个关节已保存、IMU 已校准、零姿态参考已确认。

统一工作台的「关节校准」可对已经完成的普通关节只复核方向：重新记录第 1 步起点，
再按第 2 步模型正方向小幅轻摆、停稳采集，点击「保存方向 · 沿用已保存范围」。
起点可选当前安全位置，正方向不能任意选择；ID 12 将腿向身后摆，ID 22 将腿向鸭嘴方向摆。
保存只更新当前关节方向，原零点、安全范围、IMU 和其他关节保持不变；新方向的默认站姿
超出原范围、反馈过期或扭矩未确认关闭时会拒绝保存。嘴部仍需连同轻合、张开范围核对。
站姿编码器到达目标只能证明数值接近，实物两脚前后错开时仍需核对零点、方向和装配。

X5 原生工作台保存机械零点或关节方向、范围前，会先结束本次只读反馈，并等待匹配的
串口正常关闭报告及采集进程正常退出，再写入持久校准。等待期间释放反馈处理锁，
关闭超过原有 2 秒期限则拒绝写入；写盘和校准载入不会堵住活动采集或延长数据新鲜度。
保存不会自动重连或启动动作；保存后点击关节
反馈复查继续采集。新零点会取消该关节的方向和安全范围确认，必须重新完成这些采集。

原生校准动作的内部返回和 HTTP 回应使用实时状态投影。动作持有反馈锁时，不再额外复制完整运控
快照及历史连接日志，避免终点采样被网页请求阻塞；完整诊断仍由 `/api/status` 显式读取。
100 毫秒采样新鲜度、连续性、稳定性及反馈积压保护保持不变，失败的采样不会保存校准。

关节采集遇到部分舵机反馈缺失时仍立即拒绝该帧并停止。在已确认未使能、无故障且扭矩
全部关闭的情况下，结束前用原串口额外执行一次限时 100 毫秒的只读 FaultDetails 查询，
将结果或查询失败原因保存在故障和关闭报告的 `query.partial_servo_diagnostic` 中。
该查询不重试、不重连、不保存采样，也不改写原停止原因；历史读数可能已更新，因此
不能把查询结果视为故障瞬间的冻结快照或直接据此判定电压、线束故障。

统一工作台启用 `--discover-esp32` 时，每次显式连接会从 X5 的 USB 元数据识别唯一匹配的
CH340，并把串口编号、物理端口和字符节点固定到本次会话。校准、维护和运控共用这套规则，
不依赖旧的 `/dev/ttyUSB0` 或 USB1-1.3。多个候选或节点变化会停止连接；不会自动切换串口
或重新发送运动指令。板卡、启动、TF 卡和完整日志核对仍然生效，历史故障继续保留。

“读取实机，推理不动作”可先用于读取未校准的真实状态；只有完成全部校准后才计算真实状态的模型输出。
这一步不启用舵机。

## 从默认站姿到低速行走

1. 保持可靠支撑，退出只读测试后点击 **使能默认站姿**。
   下位机先把当前实测位置设为目标再启用扭矩，X5 再用至少 3 秒渐变到默认站姿。
   默认站姿或当前实测位置超出记录范围时，启动会被拒绝。
2. 检查每个关节方向和姿态。等待真实关节接近默认站姿后，页面才开放行走。
   行走前机身倾角需小于 15°。任何姿态不符合预期时，立即停止并释放。
3. 保持支撑，用小速度 **从站姿启动行走**。初始限制为前后 `±0.2 m/s`、
   横向 `±0.1 m/s`、转向 `±0.5 rad/s`。只开放行走模型；
   起身、抓取和翻滚仍只用于合成观测测试。

固定站姿由 X5 持续读取真实反馈并发送受限目标，不依赖网页计时器。
网页实时请求使用 `/api/live-status`：读取后台每 50 毫秒发布的状态快照，
按实际经过时间增加关节、IMU 和电压读数的年龄，不获取控制锁。完整重连日志仍保留在
`/api/status` 和原始诊断记录中；实时回复只携带历史重连结果。
状态发布使用独立线程，健康巡检与证据写入的耗时不会暂停发布。巡检失败仍停止并关闭连接；
读数自身过期时仍显示为过期，发布线程不会替换测量时间或重新授权运动。

原生服务在连接、打开串口、ARM 和独立健康巡检中检查完整 USB 身份。
每次 STATE、TARGET 和 STOP 发送前，检查当前字符节点和已打开文件描述符均匹配本次连接
固定的设备、inode、rdev；USB 重新枚举或描述符变化立即拒绝发送。该路径不遍历 USB sysfs，
避免网页线程与文件检查争用 Python 执行时间。ESP32 的 250 毫秒目标超时及反馈保护不变。

真实运动串口每帧只执行一次非阻塞 `os.write`，并检查完整字节数；短写、缓冲区忙或
系统调用中断立即失败，不补发、不重试。这样避免 pySerial 在整帧已被内核接收后，
因线程调度延迟误报 50 毫秒写入超时，也避免其零超时模式在 EAGAIN 时内部循环。
完整写入仍须收到匹配序号的下位机回复；原有回复超时和下位机保护保持不变。

固定站姿及不动作预览按钮允许在正常网页轮询延迟内提交一次明确请求，避免用网页中快照的
100 毫秒年龄反复切换按钮状态。连接、已知舵机故障、支撑确认和请求忙碌仍会阻挡按钮；
超过 1.5 秒未更新的显示上下文也不能提交。点击后 X5 使用控制器当前反馈重新检查
状态编号、100 毫秒反馈时效及全部启动条件，通过后才 ARM。网页历史数据不授权运动，
失败不排队、不重发；其他模型和心跳的原有时效门槛保持不变。
其他动作由网页发送控制心跳；离开或关闭页面、超过 400 ms 未收到心跳会停止。
状态查询不会延长这些动作的控制期限。网页失焦只将行走速度归零；停止按钮始终可用。
下位机超过 250 ms 未收到有效目标、反馈过期、舵机故障或扭矩丢失会自行停止。
X5 在机身倾角超过 40° 时停止，不会自动执行起身动作。
停止会取消已排队的旧启动请求，重新开始必须再次检查当前状态并明确启动。

X5 按 50 Hz 调度控制；ESP32 的整组反馈目标为 100 Hz，实际频率需以真实状态页面实测为准。
固件初始目标变化限制为 600 编码器刻度/秒（约 52.7°/秒），可能影响步态表现。
软件停机依赖可通信的总线，持续使用支撑并确保实体断电方式可触及。

## 模型与推理性能

模型来自[固定提交的官方运行时](https://github.com/LuwuDynamics/xgoduck_runtime_arduino/tree/8cdbbd84710d856581982c9eaf0d5e2970666232/python)，
包含 walk、getup、pick、roulade 四个约 775 KiB 的 ONNX 文件。
`models/manifest.json` 保存 SHA-256 与大小，载入时核对 float32 输入 `[1,61]`、输出 `[1,14]`、
关节与观察量顺序、14 个有限默认角度及正的有限动作比例；推理结果仍检查有限值。
环境使用 Python 3.10、NumPy 2.2.6、ONNX Runtime 1.22.1，CPU 单线程推理。

```sh
cd /root/xgoduck-policy
.venv/bin/python infer.py --benchmark --output benchmark.json
```

上述命令只做合成观测推理，不打开串口。每个模型预热 100 次后测量 1000 次。

| 模型 | 平均耗时 | P99 |
| --- | ---: | ---: |
| walk | 0.440 ms | 0.628 ms |
| getup | 0.449 ms | 0.552 ms |
| pick | 0.446 ms | 0.547 ms |
| roulade | 0.440 ms | 0.509 ms |

这是板端单模型、合成静止观测的结果，不代表整个控制环路或实机行走已经通过。
结果保存于 `output/x5_policy_bundle/benchmark.json`。
使用已有的策略坐标、单位观测文件可执行一次推理：

```sh
.venv/bin/python infer.py --model walk --observation observation.json
```

策略动作顺序为 `10–14, 30–33, 20–24`，嘴部 ID 34 单独保持零位。
观测使用机身角速度、单位重力、相对默认姿态的位置、关节速度、上一帧原始动作、
速度与头部指令和 6 个零。`motion.py` 根据本机校准转换原始编码器与 LSM6DSR 数据，
再复用官方 `rl_core.py` 的滤波和观测数学。
